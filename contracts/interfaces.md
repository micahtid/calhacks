# Interfaces between `gate/` and `redteam/` (issue #1 contracts)

The schemas come from GitHub issue #1. `contracts/` is the only thing both sides depend on:

| Path | What |
|---|---|
| `src/calhacks_contracts/` | uv package `calhacks-contracts`: pydantic models (source of truth), MongoDB `Repo`, families, `split_of`, ingestion CLI |
| `ts/index.ts` | TypeScript mirror of the models (erasable syntax; Node 22 runs it directly) |
| `schemas/*.schema.json` | JSON Schemas generated by `contracts-export` (`--check` in tests keeps them current) |
| `families.json` | Attack families, expected layer, which need the LLM, the held-out families |
| `allowlist.json` | Networks, assets, max 402 timeout, unknown-seller cap (policy, not data) |
| `injection_patterns.json` | Seed regexes for injection and hidden-text checks |
| `tests/fixtures/` | Fictional, test-only listings and references. Never loaded into MongoDB by any run |

Both `gate` and `redteam` depend on it by path: `calhacks-contracts = { path = "../contracts", editable = true }`.

## Data lives in MongoDB

`$MONGODB_URI` (from `.env.local` at the repo root), database `$MONGODB_DB_REDTEAM` (default `redteam`).
Collections and their documents are listed in `calhacks_contracts/db.py`. In short:

- **What the Gate may read:** `listings` (one shape for real and synthetic), `cases` (mandate per listing), and the reference
  collections `known_sellers`, `market_medians`, `wallets`.
- **What only the scorer reads:** `answer_keys`, `gen`, `listing_meta`. The Gate never loads these, so a label or a
  generator quirk can't become a feature.
- **Never in MongoDB:** the holdout. It stays encrypted in `$CALHACKS_HOLDOUT` (default `../calhacks-holdout/`), with its own
  simulated references, applied in memory via `ReferenceSet.overlay`.
- **Getting data in:** `contracts-ingest` is the only way in for real data (`listings`, `known-sellers`, `medians`).
  Real listings are recorded as honest (`answer_keys.family = "real"`). Synthetic listings are written by
  `redteam` through `Repo.put_synthetic`.
- **Train/val split:** `calhacks_contracts.splits.split_of(listing_id)`.

## Gate resolution

```
GateRequest {mandate, proposal{listing_id}, references}
  -> Gate fetches the listing itself (offline: Repo.get_listing; live: store.json + item + 402 with placeholder shipTo)
  -> GateInput {mandate, listing, references}
  -> Layer 1 (TypeScript) -> Layer 2 (Python, only if Layer 1 passes; can only turn buy into skip)
  -> GateDecision
```

`references` are built by `ReferenceSet.for_listing(listing)` from a snapshot loaded once per batch (no network calls
during decisions, G2).

### Wallet terms

- **Wallet:** where the payment goes, `checkout.pay_to`. It must equal `seller.pay_to` (`L1_PAYTO_MISMATCH`).
- **Known wallet:** a `known_sellers[].pay_to` (case-insensitive). The only form of seller trust; there is no CRS.
- **Unknown wallet:** any other wallet. Paid only up to `unknown_seller_cap_usd`, and then Layer 2 decides.
- **Lookalike wallet:** an unknown wallet with a known wallet's first and last 4 hex characters. Layer 1 treats it as
  unknown; Layer 2 flags it.

### Layer 1 rules (`RuleId`)

| Rule | Check |
|---|---|
| `L1_PAYTO_MISMATCH` | `checkout.pay_to == seller.pay_to` (case-insensitive) |
| `L1_UNKNOWN_SELLER_CAP` | `checkout.pay_to` is a known wallet, **or** `item.price <= allowlist.unknown_seller_cap_usd` |
| `L1_AMOUNT_MISMATCH` | `checkout.amount == round(item.price * 10^6)` |
| `L1_OVER_MAX` | `item.price <= mandate.max_price` |
| `L1_OVER_BUDGET` | `item.price <= mandate.spend_remaining` |
| `L1_NETWORK` / `L1_ASSET` | network and asset on the allowlist |
| `L1_ITEM_MISMATCH` | `checkout.item_id == item.id` |
| `L1_PRODUCT_MISMATCH` | `item.product_key == mandate.product_key` |
| `L1_TIMEOUT` | `checkout.max_timeout_seconds <= allowlist.max_timeout_s` (when present) |

`L1_SELLER_UNTRUSTED` remains a valid `RuleId` but is deprecated: Layer 1 no longer runs it (`L1_UNKNOWN_SELLER_CAP`
replaced it). It is kept only because the agent API's mock Gate still reports its known-store check under that id.

Layer 1 CLI: `node gate/layer1/src/cli.ts < gate_inputs.jsonl > results.jsonl`. One `{"listing_id", "checks": [Check]}` line
per input `GateInput`, same order.

## Python CLIs (`gate/`)

Each prints one JSON object on stdout. Exit 2 = bad input or failed feature self-test (stdout holds `{"error"}`).

```
gate-train --round N [--config gate/train_config.yaml] [--query JSON]
  Trains on MongoDB listings whose split_of is train (excluding holdout families), threshold from val.
  -> {"model_id", "round", "kind", "features", "n_train", "n_val", "threshold", "val": RoundMetrics}

gate-eval --model MODEL_ID|promoted [--split train|val|all] [--ids FILE] [--rows]
  -> {"model_id", "metrics": RoundMetrics, "rows"?: [{"listing_id", "label", "family", "attacker_knowledge", "decision": GateDecision}]}
```

`RoundMetrics` is defined in `calhacks_contracts.coordinator`: `layer1_catches`, `layer2_recall`, `fpr_real` (real
listings only), `per_family`, `adaptive_recall` (white_box attacks), `recall`, `fpr`, and `layer2_fpr` (false blocks among
legit listings that pass Layer 1), each a `Rate` with a Wilson 95% interval. The promotion rule's false-block bound uses
`layer2_fpr`: Layer 1 policy blocks (unknown wallets over the cap) are by design and are reported in `fpr` / `fpr_real`.

In-process equivalents for the red-team MCP server: `gatepy.evaluate.evaluate(model, items, refs)` where `items` are
`(Listing, Case, AnswerKey)` tuples, so the holdout can be scored without touching MongoDB.

## Feature plugin API (`gate/features/*.py`; the coordinator may edit these)

```python
from gatepy.registry import feature

@feature("price_ratio", monotone=-1)        # -1: risk must not rise as this value rises
def price_ratio(x: GateInput) -> float:
    m = x.references.market_median
    return x.listing.item.price / m if m else 1.0
```

Features see **only** the `GateInput`: never the answer key, generator info, listing meta or source. Pure, deterministic,
finite float, no I/O.

## Red-team side

- `AttackSpec` (issue #1, schema 2a) goes into `generate_attacks`. `family` must not be a held-out family.
  `legit_hard` expands to `families.json.legit_hard`.
- `mode = "mutate_real"` starts from `base_listing_ids` (real listings in MongoDB) and changes one thing, recorded in
  `answer_key.attack_diff`. `mode = "generate"` writes a full listing through Bitdeer.
- **Coordinator I/O:**
  - Each round starts from a `RoundInput`, built by code.
  - The coordinator returns a `CoordinatorOutput`.
  - Code assembles the `RoundReport`, filling in `metrics`, the promotion `decision` and `cost` itself, so the LLM never
    writes the headline numbers.
